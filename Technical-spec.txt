JAPA — Technical Design & Architecture
Oct 16, 2026 · @ikenna
Purpose and design principles
JAPA is a mobile-first browser game. It must load on a cheap Android phone over expensive data and survive going from zero to one million players in 72 hours without falling over. Lagos Life proved that this kind of spike happens, and its early outages and in-game money exploit are the two failures this architecture is designed to prevent.
Scope: the MVP (Acts 1–3, a short Act 4, UK, Canada, Germany and Remote Work routes, the embassy minigame, result cards, Sponsor a Friend, payments, rewarded ads, sponsor placements) and the platform it needs to scale to 1M+ daily players.
Design principles
1. Static first. Everything a guest needs to play a run is static files on a CDN. If every backend service is down, people can still play, and progress syncs later.
2. Server load scales with runs, not swipes. The client plays the run locally. The server is involved only when something with lasting value changes: currency, unlocks, leaderboards, social actions.
3. Never trust the client with value. Anything that persists — money, unlocks, ranks — is validated on the server by replaying the run deterministically.
4. Naija specs are hard limits, not targets. Initial load under 3 MB, works on a 2 GB RAM Android, tolerates dropped connections mid-danfo.
5. Degrade, don't die. Every non-core feature (feed, transfers, leaderboards, share cards) sits behind a kill switch, so the core game stays up when one part fails.
6. Boring, managed infrastructure. Use managed services the team doesn't have to operate. The scarce resource is engineering time, not servers.
7. Content is data. Cards, events and sponsor placements ship as versioned content packs, not code. Writers and live-ops change the game without a deploy.
Non-functional requirements
The binding targets are a 3 MB first load, a 4-second start on 3G, and holding 50,000 concurrent players at launch-spike peak with headroom to 1M daily players. Everything else is sized from these.

Architecture overview
JAPA is four layers: a PWA that plays runs on the phone, a Cloudflare edge that serves almost all traffic, a stateless API with background workers, and managed data stores. The database is reached only through the API and the queue, never directly by players.
Players load the game from the edge and play locally; the API only sees run commits, purchases and social actions, and slow work goes through the queue so spikes wait in line instead of hitting the database.

The Gate minigame
• 5–7 timed questions (8 seconds each) from an officer or interviewer with a personality: strict, bored, suspicious, friendly.
• Each answer shifts a hidden approval score. The final score combines answers (50%), stats (35%, mostly Documents or Skill) and seeded luck (15%).
• A hidden fake-document flag adds a chance of instant refusal and a ban from that route for the rest of the run.
• Outcomes: approved, refused (retry costs money and time), or administrative processing (delay, one extra card set).

Deterministic simulation (the core idea)
• Every run starts from a server-issued run_seed plus a content pack version.
• All randomness — visa outcomes, events, card draws — comes from a seeded generator (PCG32), never Math.random().
• The client records an action log (card id + choice + step, a few bytes each).
• Given the same seed, content version and action log, the simulation produces the same outcome on any machine. That lets the server replay a run to check it (see Backend).

Feel (juice)
• Card swipes respond on the first frame of touch, with spring physics and a tilt that hints at the outcome.
• Stat changes animate with a pulse and short sound; big moments (visa stamp, rejection) get screen shake, particles and haptics via the Vibration API.
• Respect prefers-reduced-motion and add a low-power mode that drops particles on weak devices (detected by frame timing).
Onboarding target: a new player is swiping a meaningful card within 30 seconds of the page opening — no sign-up, no tutorial screen; the first three cards teach swiping.
Simulation engine and content format
The simulation is a pure, deterministic TypeScript package (sim/) shared by client and server: same seed + same content version + same action log = same result, on every device. Writers change the game by editing content packs, never engine code.
Engine contract
• startRun(seed, contentVersion, trait) → RunState
• nextCard(state) → Card
• applyChoice(state, cardId, choice) → RunState — the only way state changes
• evaluateEnding(state) → Ending | null
• replay(seed, contentVersion, trait, actions[]) → { state, ending, valid, error? }
Rules the engine must keep:
• No Math.random(), Date.now(), network or DOM access inside sim/. Randomness comes only from a seeded PCG32 generator carried in RunState.
• Integer arithmetic only (money in kobo or cents); no floating-point drift between devices.
• Every content version stays playable forever on the server, so old runs can still be replayed and validated.
• A replay test suite of 1,000+ recorded runs runs in CI on every change; any difference blocks the merge.
Action log format
Each action is [step, cardId, choice, elapsedMs] — about 12 bytes compressed. A full run is typically 150–300 actions, under 4 KB. elapsedMs is kept for anti-bot analysis (inhuman speed), not for the outcome.

Content pipeline
1. Writers edit cards in a shared sheet, one row per card, with columns matching the schema.
2. A converter turns the sheet into JSON and a validator checks it: schema, broken next links, unreachable cards, impossible requirements, effect ranges, banned words.
3. A balance simulator plays 100,000 bot runs per route and reports ending distribution, run length and dead ends. A route ships only if every ending is reachable and no single ending exceeds 40%.
4. The pack is signed, uploaded to R2 under a new version, and turned on by updating the manifest — with a feature flag for gradual rollout and instant rollback.
Sponsor slots are named placeholders on cards (for example remittance_app). The sponsor service fills them per country and campaign at pack build time, so the engine never knows about brands and replays stay deterministic.
Backend services, data and economy
The backend is one stateless Node.js API (Fastify, TypeScript) deployed as containers, split into modules — not microservices — with heavy or slow work pushed to background workers through a queue. Splitting into separate services happens only when a module's load profile demands it.

Economy: a real ledger, not a balance column
• Every change of value is a transaction with two or more ledger entries that sum to zero. Money is never created by editing a number; it moves from a system account (rewards, purchases) to a player account.
• Balances are derived from entries and cached; a nightly job checks every account still sums correctly and alerts on any difference.
• Every write carries an idempotency key, so a retried request or a double-tap can never pay twice.
• Two currencies: Game Naira (earned in play, cannot be bought or withdrawn) and Coins (premium, bought with real money, spent on cosmetics and boosts). Neither can ever be cashed out — this keeps the game out of gambling and money-transmission regulation.
• Player-to-player transfers (Sponsor a Friend, Black Tax) are capped per day, require an account older than a set age, and are rate-limited and screened for farming patterns.
Anti-cheat by replay
1. The server issues a seed when a run starts and records it.
2. The client plays offline and submits the action log at checkpoints and at the ending.
3. A worker replays the log through the same simulation module. If the outcome matches and the actions are legal, rewards post to the ledger; if not, the run is flagged and nothing is credited.
4. Rewards per run, per hour and per day are capped regardless of outcome, so even a perfect exploit is bounded.
This closes the class of bug behind Lagos Life's money exploit: the client can show whatever it likes, but only server-verified results ever reach the ledger.
Social systems
Players interact asynchronously and only with people they have added, using preset messages and stickers, not open chat. Every interaction changes something in the game for both sides, is capped per day, and is built on two primitives: a social action (a ledger-backed or state-changing request between two players) and a feed event (a read-only notice to a crew).

Friend graph
• Players connect by invite link, QR code or crew code — no searching for strangers by name or phone.
• Friendships are mutual and require acceptance; blocking removes the friendship and hides all past feed events from each other.
• Crews and friends lists are capped (200 friends, 8 per crew) so feed fan-out stays bounded.
Social action lifecycle
1. pending — created by the sender with an idempotency key; any value moves into an escrow ledger account.
2. accepted / declined / expired — set by the receiver or by a worker after the time limit.
3. On accepted, escrow moves to the receiver; on declined or expired, it returns to the sender. Both are ledger transactions, so no value is ever lost or duplicated.
Messages and safety
• Only preset messages and stickers (about 60 at launch), localised in Nigerian English and Pidgin. Custom text is limited to display names and crew names, both filtered.
• Report and block on every player surface; three reports from distinct accounts hide a display name until reviewed.
• Accounts under 7 days old, or still guests, cannot send Game Naira — this stops farming with throwaway accounts.
Deliberately not built at launch: open chat with strangers, free trading between players, a real-time shared world, and dating features. Each adds moderation, fraud or infrastructure risk out of proportion to its value for a card game.
Scaling strategy and viral-spike playbook
The plan for a spike is that most traffic never reaches our servers: the CDN serves the game, the client plays the run, and the backend only handles commits, which are small, batched and queued. The database is the one part that cannot scale instantly, so the design protects it above everything else.

Spike playbook (run in this order when traffic surges)
1. Confirm CDN cache hit rate is above 98%; purge nothing.
2. Raise autoscaling limits for API and workers; watch database connection count and CPU.
3. Turn on degraded mode via feature flags, cheapest losses first: slow feed polling to 5 min, pause leaderboard live updates, queue share-card renders, pause new player-to-player transfers.
4. If the database is still stressed, switch run commits to end-of-run only (skip mid-run checkpoints).
5. Last resort: enable the Cloudflare Waiting Room for account actions only. Guests keep playing; their progress stays on the device and syncs later.
Protecting the system from abuse at scale
• Rate limits per IP, device and account at the edge (Cloudflare) and in Redis.
• Cloudflare Turnstile on account upgrade and transfers — invisible to most players, blocks bot farms.
• Guest accounts get no transferable value until upgraded, so farming throwaway accounts earns nothing.
Before launch: load-test with k6 at 3× the launch target (150k simulated concurrent players, 4,500 commits/s) and run a game-day where we kill the database replica, Redis and one region to prove each degraded mode works.
Monetization and distribution
Revenue comes from three streams, in this order of reliability: sponsor placements, rewarded ads, then Coin purchases. Card penetration is low for web purchases in Nigeria, so the game must earn from players who never pay; Coin purchases are aimed mainly at diaspora players.
Payments
• Paystack is primary (cards, bank transfer, USSD), with Flutterwave as a fallback behind the same internal PaymentProvider interface.
• Flow: client asks the API for a checkout → API creates a pending purchase with an idempotency key → player pays on the provider's page → the provider's webhook (signature verified) confirms → the ledger credits Coins once.
• Never credit Coins from a client redirect alone; only the verified webhook or a server-side verification call counts.
• A daily reconciliation job matches provider settlements against the ledger and alerts on any mismatch.
Rewarded ads
• Players can watch a short ad for one extra embassy attempt, a stat rescue or bonus Game Naira — capped per day.
• Ads run behind an AdProvider interface: an H5 rewarded-ad network on our own site, and each portal's own ad SDK on portal builds.
• Rewards credit only after the ad network's completion callback, verified on the server where the network supports it.
Sponsor placements (the main revenue line)
• Sponsors are content, not banners: a remittance app is the in-game way to send money home, an IELTS brand is a study card, a relocation agency is a "verified agent".
• Placements are rows in the sponsor service (brand, card ids, countries, dates, cap) and ship inside content packs, so a new deal goes live without a code release.
• Impressions and clicks go to the analytics stream with de-duplication, feeding a sponsor report per campaign.
Distribution
• Own site (direct traffic): the PWA at our domain, installable to the home screen. This is where accounts, Coins and the social features live.
• Portals (Poki, CrazyGames): a portal build from the same code, with a platform adapter that swaps in the portal's ad SDK and turns off external payments and accounts, as portals require. Check each portal's current rules before submission.
• Share loop: every ending produces a result card. The share link opens a lightweight page with Open Graph tags, so WhatsApp, X and Instagram show the card image as a preview; tapping it opens the game straight into a new run with a referral code attached.
• Referral tracking: referral codes on share links, attribution stored on account creation, rewards credited only after the new player finishes a first run (stops self-referral farming).
Security, privacy and integrity
The game holds paid value and personal data on Nigerian players, so it is built to the Nigeria Data Protection Act 2023 and to OWASP ASVS Level 2 from day one, with controls mapped so an ISO 27001 audit later is a paperwork exercise, not a rebuild.
Data protection (NDPA)
• Collect the minimum: no real name required; phone numbers stored as salted hashes plus an encrypted copy for OTP only.
• Clear consent at upgrade; a privacy notice in plain English; data export and account deletion available in settings.
• A records-of-processing register and a named data protection contact; register with the NDPC if the player base crosses the threshold that requires it.
• Analytics use pseudonymous ids; no selling of personal data to sponsors — sponsors get aggregate reports only.
Application security
• All traffic over TLS; HSTS; strict Content Security Policy that allows only our CDN and the approved ad and payment domains.
• Short-lived access tokens (15 min) with rotating refresh tokens; device binding for guest accounts.
• Every economy endpoint requires an idempotency key and is authorised per player; no client-sent amounts are trusted.
• Payment and ad webhooks verified by signature and checked against the provider's API before crediting.
• Secrets in a managed secret store, never in code or the client bundle; keys rotated quarterly and after any staff change.
• Dependency and container scanning in CI; a public security.txt and a simple bug-bounty email.
Game integrity
• Server-side replay of every run that earns value (see Backend).
• Velocity rules on transfers and rewards; automated flags plus a small admin console to freeze accounts and reverse fraudulent ledger transactions with a full audit trail.
• Admin actions require two-factor sign-in and are logged immutably.
Content safety
• The proof-of-funds and "agent" storylines are satire with consequences; no card describes real methods of document fraud.
• Player-written text (names, group chat lines) passes a profanity and abuse filter; reporting and blocking are in the social features from launch.

• One monorepo: client/, server/, sim/ (the shared simulation), content/, infra/.
• GitHub Actions: type-check, unit tests, simulation replay tests over recorded runs, bundle-size budget check, security scan.
• Every pull request gets a preview deploy; production releases go out behind feature flags, with a 10% canary for server changes.
• Database changes go through versioned, backwards-compatible migrations (expand, migrate, contract), so a release can always be rolled back.
• Content packs have their own pipeline: writers edit cards in a sheet, a validator checks references and balance, and a signed pack is published to R2 with a version number.
Build phases, risks and open decisions
The target is a public launch in late November, ahead of Detty December, with each phase passing a gate before the next begins.
Phases
1. Prototype (Oct 16 – 25). Swipe loop, stats, 30 cards, deterministic simulation in sim/. Gate: 10 people outside the team play twice unprompted.
2. MVP build (Oct 26 – Nov 15). Acts 1–3 and a short Act 4, three countries plus the Remote Work route, embassy minigame, guest accounts, ledger, run replay, result cards, Paystack, one sponsor placement. Gate: bundle within budget; replay matches on 100% of recorded runs.
3. Hardening (Nov 10 – 18, overlapping). k6 load test at 3×, game-day failure drills, security review, NDPA notice. Gate: all four SLOs hold under load; every degraded mode tested.
4. Soft launch (Nov 19 – 23). Invite-only to about 5,000 players through friends and a few creators. Gate: day-1 retention ≥ 35%, crash rate < 1%, no ledger mismatches.
5. Public launch (around Nov 25). Teaser clips on X and TikTok from day 1 of the build; portal builds submitted after launch week.
6. Live ops (December). IJGB / Detty December event, Sponsor a Friend at full scale, first sponsor campaigns.
